# Provenance on copies

RAMNest permits only `com.apple.provenance` to differ between distinct copies. This policy was explicitly approved after host probes showed that macOS can add provenance when a different process creates the destination, even when the public copy API reports success. This is observed host behavior, not a claimed Apple API guarantee.

RAMNest leaves provenance to normal OS copy behavior. It does not strip it, decode its private format, explicitly replay it into disk copies, or change security settings. Quarantine and all other attributes, file content, modes, flags, namespace and hardlink relationships remain strict.

Raw observations include provenance. Source stability checks remain exact. A new snapshot records the destination's own verified metadata, so later changes to that snapshot's provenance still fail integrity verification. The optional `Entry.provenanceBytes` field records the measured name-plus-value byte cost; older manifests without it retain exact attribute hashes and totals. RAMNest measures an old verified source before applying copy comparison, and never assumes a private payload length. Capacity checks charge the attributes actually held by each object.

Restore journals distinguish the original source observation from the new materialization. Store relocation preserves immutable revision manifests and mode maps byte-for-byte. Its private `.ramnest-copy-observations.json` record binds each moved revision's observed metadata to the unchanged manifest digest, mode-map digest and destination store identity. Source retirement requires exact destination observations in addition to copy fidelity and existing identity/fence checks. Native runtime xattr operations continue to expose the attributes actually held in RAM.

Missing authority, malformed accounting, changed metadata, or an unacknowledged allocation fails closed and retains recovery data. Verification of an inaccessible published tree remains subject to the existing permission and recovery rules.

## Separately approved verified renames

On 2026-11-08 the user explicitly approved provenance-only differences during verified RAMNest renames, after an owned cross-creator NFS reproduction showed authentic OS additions on the directly renamed inodes. This is a separate authorization from copy fidelity. Capture and raw source checks outside the coordinator's own rename window remain exact.

The coordinator checkpoints a typed, versioned rename intent before mutation. It records raw metadata and per-node device, inode, link count, owner/group, mode, flags, size and timestamps. Opaque excluded top-level directories retain their stat-only admission contract: no root xattr listing/reading and no subtree traversal. Top-level moves pin the actual inode and use no-replace rename; excluded roots may use before/after no-follow stat identity checks when event-only opening is denied. Whole-directory FSKit moves retain the existing wrapper/layout and root-inode authority.

Only the directly renamed inode (and its hardlink aliases) may have different provenance accounting/digests during that operation. The comparison uses measured costs without decoding, replaying, stripping or assuming the length of provenance. Rename-caused ctime changes are admitted only on those inodes; sizes and mtimes remain exact. Every other field stays strict. A complete raw post-rename observation is durable before helper startup or publication commit, and later verification compares that observation and inode evidence exactly.

`initialSourceManifest` remains the pre-evacuation source observation. `originalRename` holds evacuation intent/completion; `publicationRename` holds a separate reverse-rename or restore publication operation. Completed evidence transfers to the cleanup candidate before active receipt fields are cleared at idle. Cleanup binds the retained and restored observations to their verified revisions through the separately approved copy relation, then requires their own raw observations and identities. The original public-root metadata is distinct from a newly created private holding wrapper.

Absent receipt fields retain the legacy strict contract, including journals without a session. Legacy restore/rollback does not mint a UUID or acquire new provenance variance authority. Explicit null, an unknown receipt version/operation or malformed bindings fails closed. A pending intent without completion grants no provenance exception: recovery can continue only when its entire raw before manifest and bound inode metadata still match, apart from the actual moved inode's normal rename ctime. This strict recovery check creates no completed receipt and cannot activate a helper. A provenance-only difference without completed evidence still requires review. Existing pre-fix pending recovery receives no new waiver. Inaccessible restrictive publication retains its existing rules and receives no new provenance exception without independent readable post-rename evidence.
