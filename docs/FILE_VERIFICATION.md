# File verification contract

`FileVerification` has two wire values: `sha256` and `sizeAndModTime`. Settings selects a global policy for the next new mount. SHA-256 is the default and the missing-field legacy interpretation. Explicit null, unknown strings and wrong JSON types reject in configuration, journals, manifests and stored revisions. Regular-file checksums must agree with their policy: SHA records contain a supported SHA digest; metadata records contain an empty checksum. Removing the discriminator from a metadata manifest cannot make it a SHA manifest.

The journal fixes the session policy before source capture. Immutable revision metadata, inline transaction manifests, rename receipts and cleanup plans carry that authority. SHA-only inline manifests retain their historical canonical encoding (absent policy means SHA) so old publication-receipt digests stay valid. New stored revision records explicitly encode their policy. A setting change never relabels a snapshot, changes a running helper, or changes recovery. Recovery rejects session/revision policy disagreement. An explicit historical export uses the chosen revision's own policy.

In `sizeAndModTime`, regular-file verification checks size and nanosecond modification time along with the existing namespace, modes, allowed flags, xattrs, hardlink partitions, ownership/security admission and identity/race checks. It computes zero SHA-256 over regular-file payloads in the app/helper session: Swift scanning/copy readback, snapshot capture/verification, save/export adoption, restore, sibling cleanup, and native RAM page creation/read/overwrite/truncate/import/export verification all follow that policy. Sparse allocation accounting still reads nonzero logical pages as needed; this is not a promise of no file reads. Relocation resolves known revision payloads from stored revision authority and pins the policy per inventory item; copying/retrying/retiring weak payloads skips their content digests. Other opaque store files, including unknown files outside revision payload namespaces, retain separate storage-relocation SHA integrity. They are not reclassified using the current Settings preference; map/control/metadata files also retain SHA-256.

A same-size edit with the original modification time restored can be accepted in metadata mode. This applies to copied files, incremental candidates, saved snapshots and recovery/cleanup decisions. SHA mode rejects the same mutation. In-flight changes still fail the pinned identity/ctime/mtime checks; metadata mode does not waive errors or writer-race checks.

Folder `Snapshot comparison` / CLI `--file-comparison-method` continues to control incremental selection. It does not select integrity. SHA sessions keep their existing verified-digest reuse. Metadata sessions can reuse candidates selected by size/mtime; requesting checksum selection without file digests falls back to copying current source data. Crossing policies disables reuse of the prior candidate rather than reinterpreting or hashing an incompatible historical payload for the new metadata session.

The native helper's file export/readback verifier follows the immutable startup policy. Metadata mode does not hash or read disk file payloads for export verification, including no-op validation; it checks size/mtime and the existing other metadata/namespace rules. SHA mode retains independent disk content SHA and sparse-hole verification. `--verification-capabilities` must return exactly `file-verification-v1` before a metadata session can evacuate originals. The startup flag is `--file-verification sizeAndModTime`; malformed, missing, duplicate and unknown policy values reject before daemonization. Guarded startup is required. The authenticated `verification-policy` command returns the version and bound policy before population, and is rechecked for live operations/exports. A legacy helper remains usable for SHA sessions and cannot silently service a metadata session.

Native `MemoryFS` binds the policy at construction. Each `MappedPage` binds it when created and carries it through captures, descriptor copies and export clones; staged writes and truncation create replacement pages with the same tree policy. Metadata pages neither create nor compare payload SHA, including `encode`, `decode`, `verifyRaw`, `readSlice` and export's `verifyMemory`. Direct page construction and trees without an explicit policy default to SHA-256. Bounds, decoded LZ4 length, quota/accounting, identity, capture/epoch checks and bounded write retries still apply.

**Weaker RAM integrity:** a raw payload mutation is intentionally undetected in metadata mode. A compressed mutation is detected only if it violates structural checks or fails to decode to the required length; another valid decoded payload can be accepted and exported. There is no guarantee of EIO for every memory mutation. SHA sessions retain payload checksum creation/comparison and corruption rejection.

This is zero **regular-file payload SHA**, not zero SHA everywhere. Symlink targets, xattrs/resource-fork metadata, logical mode maps, manifest/publication/control records and package/security checks retain their hashes. Historical SHA revisions still verify using their own recorded policy, including retention/relocation in a repository with mixed policies; a new weak session cannot relabel them.

Debug profiling keeps the v2 frame and metric identifiers. `integrityAlgorithm` reports the bound runtime policy (`sha256` or `sizeAndModTime`); the app validates it against the session journal, rejects unknown/mismatched values, and rejects metadata frames reporting payload SHA calls/bytes. The SHA row is N/A when disabled; report text describes structural/metadata checks for that policy.

Validation: `bash scripts/file-verification-tests.sh` builds isolated standalone Swift/native fixtures without mounting. It exercises persistence/cold Settings relaunch, strict decoding, policy negotiation/parser/authenticated framing, both policies through capture/export/adoption/save/cold rollback/checkpoint restore/relocation, size/mtime mismatch rejection, the intended blind spot, Swift file SHA counters, native actual payload SHA counters across writes/staging/truncation/import/fresh export/clone/no-op and capture retries, default strong corruption detection, metadata raw-corruption acceptance, structural decode rejection, frozen legacy manifest/observation bytes, restrictive receipt recovery and both runtime profile algorithms. `RAMNEST_HASH_TRACE` includes the policy and `fileContentSHA256Bytes` for each Swift scan. Native export stats report `fileVerificationSHA256Bytes` separately from the internal block hashing test counter. Host mount/eject and GUI rendering remain separate verification.
